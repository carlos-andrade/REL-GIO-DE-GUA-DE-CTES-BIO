# CARTA DE REGRAS DE SALVAMENTO — V1

**Projeto:** RELÓGIO DE ÁGUA DE CTESÍBIO
**Data de vigência:** 27/09/2026
**Repositório oficial:** carlos-andrade/RELOGIO_DE_AGUA_DE_CTESIBIO
**Status:** REGRA OPERACIONAL DO PROJETO
**Carta superior:** GOVERNANCA/CARTA_REGENTE_DO_PROJETO_V1.md

## 1. Relação com a Carta Regente

Esta carta permanece vigente como regra específica de salvamento e preservação documental, subordinada à Carta Regente do Projeto.

Em caso de conflito, prevalece a Carta Regente.

## 2. Regra fundamental

Todo conteúdo produzido nos chats deste projeto que tenha valor documental, técnico, histórico, arquitetural, experimental, de engenharia, de especificação, de teste ou de decisão deve ser registrado no repositório oficial.

O chat é o ambiente de trabalho. O GitHub é o registro oficial do projeto.

## 3. Salvamento obrigatório

Sempre que uma entrega gerar um artefato reutilizável:
1. identificar o tipo de documento;
2. escolher a pasta correspondente;
3. criar ou atualizar o arquivo;
4. registrar data e versão;
5. preservar o histórico por commits;
6. confirmar caminho e commit.

## 4. Organização

Usar as pastas existentes e criar novas categorias somente quando justificadas. Conteúdos devem permanecer separados por finalidade, incluindo governança, documentação, pesquisa, engenharia, dados, protótipos, testes, calibração e release.

## 5. Integridade documental

Não apagar histórico relevante sem justificativa. Alterações relevantes devem gerar nova versão ou registro claro da mudança.

## 6. Rastreabilidade

Artefatos importantes devem conter, quando aplicável, arquivo, projeto, finalidade, data, versão, caminho, status, referências e histórico de alterações.

## 7. Confirmação

Após cada gravação no GitHub, informar arquivo, caminho, versão, commit e status.

Não declarar que algo foi salvo sem confirmação do GitHub.

## 8. Continuidade

Novos chats devem consultar o repositório antes de assumir contexto. O conteúdo versionado do Git é a referência principal.

## 9. Segurança contra perda

Nenhuma decisão técnica relevante deve existir exclusivamente no chat.

## 10. Auditoria

O histórico Git deve permitir reconstruir o que foi criado, quando, qual versão estava vigente e quais decisões foram substituídas.

## 11. Princípio

> O chat serve para trabalhar. O repositório serve para preservar.
